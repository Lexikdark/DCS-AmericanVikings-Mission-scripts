Mission State Persistence v4.0

MissionStatePersistence(v.4.0).lua  ·  Saves CJTF-BLUE ground groups & all airbase warehouses every 10 minutes and restores them on the next server restart

How It Works

Groups
All live CJTF-BLUE ground units (position, heading, fuel, type) are serialized to a Lua file every 10 minutes. On the next mission start a 15-second delayed restore destroys all existing BLUE ground groups and respawns them from the save file at their last known positions.
Warehouses
The full inventory — liquids (fuel, O₂, MW-50), weapons, and aircraft — of every DCS airbase is captured and saved. On restore each airbase's warehouse is refilled to match the saved state.
DGSS-CTLD integration: If DGSS_CTLD is loaded (detected via global existence check), groups spawned by CTLD under DGSS_CTLD.COUNTRY are also included in saves, so player-deployed JTAC teams and vehicles survive a server restart.
Change detection: Each save cycle computes a position+unit-count hash per group. Only groups whose state has changed since the previous save are marked "new/changed" in the log — unchanged groups are still written (the SavedGroups table is rebuilt from scratch each cycle) but the tracking avoids redundant file I/O when nothing moved.

Config — Save File Paths

MISSIONPERSIST.saveDir…\Mission Saves\Directory where both save files are written.▼ details

Resolved at runtime as lfs.writedir() .. "Mission Saves\\". On a typical Windows DCS install this expands to:

C:\Users\<user>\Saved Games\DCS.openbeta\Mission Saves\

The directory is created automatically on first load if it does not exist. If creation fails, the script disables itself and logs an error.

MISSIONPERSIST.groupFileMissionGroups.luaSerialized Lua file containing all saved ground group states.▼ details

Full path: saveDir .. "MissionGroups.lua". The file is plain Lua that, when executed, rebuilds MISSIONPERSIST.SavedGroups. Each group entry stores: name, country, category, coalition, task, x/z position, and a full unit list (type, name, x/z, heading, skill, fuel, life).

MISSIONPERSIST.warehouseFileMissionWarehouses.luaSerialized Lua file containing all airbase warehouse inventories.▼ details

Full path: saveDir .. "MissionWarehouses.lua". Stores the full Warehouse:getInventory() result for each airbase, keyed by airbase name. Includes three sub-tables: liquids, weapon, aircraft.

Config — Save Interval

MISSIONPERSIST.saveInterval600 s (10 min)How often the periodic save loop fires.▼ details

Set at the top of the script. The first periodic save fires 10 minutes after restoration completes (15 s after mission start). Change to a lower value (e.g. 300) for more frequent saves on active servers, or higher (e.g. 900) to reduce disk I/O. Both the group file and warehouse file are written on every save cycle.

Startup Flow

1
Dependency check — verifies lfs and mist globals exist. If either is missing, the script logs an error and returns (fully disabled).
2
Ensure save directory — calls MISSIONPERSIST.ensureDirectory(). Creates Mission Saves\ if absent. Disables if creation fails.
3
Capture initial groups — MISSIONPERSIST.captureInitialGroups() records all ME-placed CJTF-BLUE ground groups into MISSIONPERSIST.initialGroups. This snapshot is taken before any restores run, so the script knows which groups were in the mission file originally.
4
Load saved files — loadGroups() and loadWarehouses() read the two save files (if they exist) and loadstring-execute them to populate MISSIONPERSIST.SavedGroups and MISSIONPERSIST.SavedWarehouses. If files don't exist (first run), both tables are initialised empty.
5
Delayed restore (T+15 s) — a timer.scheduleFunction fires 15 seconds after mission start to give DCS time to fully initialise. This calls restoreGroups() then restoreWarehouses().
6
Periodic save loop starts — after restoration completes, the first periodic save is scheduled for T+10 min. Each save reschedules itself.

Save Flow (every 10 minutes)

1
MISSIONPERSIST.captureGroups() — clears SavedGroups, iterates mist.DBs.groupsByName, filters for living BLUE (and CTLD) ground groups, captures unit state, applies change-detection hash.
2
MISSIONPERSIST.serializeWithCycles() — converts SavedGroups to a Lua string that self-assigns the table when executed. Handles circular references via the saved visited-table guard.
3
MISSIONPERSIST.writeFile() — opens MissionGroups.lua in write mode and overwrites it. Logs a warning if io.open fails.
4
Same process for warehouses: captureWarehouses() → serializeWithCycles() → writeFile() to MissionWarehouses.lua.

Restore Flow (T+15 s on mission start)

1
Destroy all existing BLUE ground groups — iterates mist.DBs.groupsByName again and calls group:destroy() on every existing CJTF-BLUE (and CTLD) ground group. This clears both ME-placed groups and any remnants. Wrapped in pcall to avoid errors on already-dead groups.
2
Spawn from save file — for each entry in SavedGroups, builds a group template and calls coalition.addGroup(country, Group.Category.GROUND, template). Units are placed at their saved x/y coordinates with their saved headings. Skill is set to the saved value (typically "Average").
3
Restore unit fuel — after each group spawns, iterates its units and calls unit:setFuel(savedFuel) to restore fuel levels. Wrapped in pcall.
4
Restore warehouses — for each saved airbase, locates it via world.getAirbases(), gets its Warehouse object, then calls setLiquidAmount, setItem (weapons), setItem (aircraft) to rebuild the inventory.
On first server launch (no save files yet) — SavedGroups and SavedWarehouses will be empty tables. The restore step destroys all ME-placed BLUE ground groups and spawns nothing back. This means the first session will have no BLUE ground forces until the first 10-minute save creates the files. To avoid this, either pre-seed the save files or remove the destroy-all step in restoreGroups() when no save file exists.

Group Saving — Detail

Data captured per unit:

-- Per-unit entry in SavedGroups
{
    type    = "M1A2 SEP v2",      -- DCS unit type name
    name    = "JTAC_Team_0001_U1",-- unit name (used to identify on restore)
    x       = 42568.3,            -- world X position
    y       = 37291.8,            -- world Z position (stored as y for coalition.addGroup)
    heading = 1.57,               -- radians
    skill   = "Average",          -- always "Average" on restore regardless of original
    fuel    = 0.85,               -- 0.0–1.0
    life    = 1.0,                -- health value (not used to filter; dead units excluded upstream)
}
Units are restored with playerCanDrive = true, meaning any player can take direct control of restored ground vehicles. Group tasks are always set to "Ground Nothing" — original AI waypoints are not preserved.

Warehouse Saving — Detail

Data captured per airbase via Warehouse:getInventory():

-- SavedWarehouses["KANDAHAR"] = {
--   liquids  = { [0]=12000, [1]=8000, ... },   -- liquid type IDs → litres
--   weapon   = { ["AIM-120C"]=24, ... },        -- weapon name → count
--   aircraft = { ["F/A-18C"]=4, ... },          -- aircraft type → count
-- }

Restoration uses:

  • Warehouse:setLiquidAmount(liquidType, amount) for each liquid
  • Warehouse:setItem(name, count) for weapons and aircraft

Change Detection

Each save cycle maintains MISSIONPERSIST.lastSavedState — a table keyed by group name storing a lightweight hash string:

local currentHash = string.format("%.0f_%.0f_%d", groupPos.x, groupPos.z, #unitTable)

The hash encodes the group's world X, world Z (rounded to nearest metre), and living unit count. A group is considered changed when any of these three values differs from the previous cycle. A group with the same position and same unit count is still written (SavedGroups is rebuilt fully each cycle) but is counted separately in the log output as "unchanged" for monitoring.

The hash intentionally does NOT encode heading or fuel — those micro-changes on stationary units would cause every group to appear "changed" every cycle. If you need finer change detection (e.g. for fuel-critical scenarios), extend the hash to include fuel from the first unit.

Serialization

The script uses a custom cycle-safe serializer (MISSIONPERSIST.serializeWithCycles) derived from the SWS/SGS tradition. It walks the table recursively and emits assignment statements:

-- Output format (simplified):
MISSIONPERSIST.SavedGroups = {}
MISSIONPERSIST.SavedGroups["GroupName"] = {}
MISSIONPERSIST.SavedGroups["GroupName"]["name"] = "GroupName"
MISSIONPERSIST.SavedGroups["GroupName"]["units"] = {}
...

On load, the file is read as a string and executed via loadstring(content)() inside a pcall. This pattern is standard in DCS persistence scripts and avoids having to write a dedicated parser.

The save files are standard Lua. They can be manually edited to adjust positions, restore lost groups, or seed state before a campaign's first boot. Be careful with string quoting — use the same conventions string.format('%q', s) uses.

Mission Editor Checklist

  1. MIST must be loaded first — MISSION START → DO SCRIPT FILE → mist.lua.
  2. Load persistence script — MISSION START → DO SCRIPT FILE → MissionStatePersistence(v.4.0).lua.
  3. Script sanitation — ensure the DCS server's MissionScripting.lua has io and lfs enabled (not sanitized out). Without these the script self-disables on startup.
  4. No additional ME setup required — the script reads whatever BLUE ground groups exist at mission start and persists them. No trigger zones, flags, or units need to be added specifically for persistence.
  5. Campaign start — on the absolute first run (no save files), optionally pre-populate the save folder with seed files, or accept that the first 10 minutes will have no persistent groups.
  6. DGSS-CTLD — load CTLD before this script if you want CTLD-spawned groups persisted. The order matters only at the first save cycle; subsequent sessions will always catch CTLD groups regardless since DGSS_CTLD will be defined by the time the 10-minute timer fires.
