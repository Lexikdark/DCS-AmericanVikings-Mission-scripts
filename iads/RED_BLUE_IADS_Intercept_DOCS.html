RED / BLUE IADS + Intercept System

RED_BLUE_IADS_Intercept.lua  ·  Syria map  ·  Requires MIST 4.5

How It Works

Four parallel systems run simultaneously via DCS timer loops:

  1. IADS Network — EWR and SAM groups discover each other. EWR shares contacts to nearby SAMs. The SAM with the best engagement geometry fires.
  2. ARM Defence — an incoming-weapon tracking loop watches every in-flight weapon. If an ARM is detected heading for a radar, that radar shuts down and optionally moves.
  3. Air Intercept — trigger zones mark airspace sectors. When an enemy aircraft enters a zone, the assigned late-activate flight scrambles from the nearest base.
  4. RTB Check — airborne intercept flights are monitored for fuel. At bingo they are ordered to RTB.
Both coalitions run independent but symmetrical copies of all four systems. RED has 16 squadrons, BLUE has 4. SAM and EWR groups for both sides are auto-discovered by naming prefix at startup and periodically refreshed. AWACS aircraft are kept on orbit by a separate 300-second keeper loop. A three-way Lebanon sub-IADS runs independently alongside the main RED network.

IADS Architecture

How every element connects inside a single coalition network. All three networks (RED, BLUE, LEBANON) follow this same pattern independently.

Three independent copies of the above network run in parallel: RED (61 SAMs, 16 EWR, targets BLUE aircraft), BLUE (12 SAMs, 7 EWR, targets RED aircraft), and LEBANON (9 SAMs, 10 EWR, isolated RED sub-IADS with Lebanon zone gating). They share no contacts or engagement assignments.

Configuration — Update Intervals

Click any row to expand the detailed explanation.

UPDATE_INTERVAL12 sMain IADS loop — contact gathering, SAM engagement decisions.▼ details

Every UPDATE_INTERVAL seconds the script runs pruneDeadNodes() to remove destroyed SAMs/EWRs, then gatherContacts() for all three coalition sub-IADS (RED, BLUE, LEBANON), shares detections to SAM nodes, scores each SAM's engagement geometry, and fires the best shooter. This is the heartbeat of the entire IADS.

Performance note (Feb 2026): Raised from 5 s to 10 s, then again to 12 s for larger networks. The main loop no longer calls buildNodeList() (which triggered 6× coalition.getGroups(GROUND) per tick). Instead, a lightweight pruneDeadNodes() removes dead groups from the existing lists without any API calls. Full node-list rebuilds only happen on the 15-minute nodeRefreshLoop. Additionally, gciInterceptLoop now caches coalition.getGroups(AIRPLANE) once per coalition per tick instead of calling it 21× per squadron.

Recommended range: 5–15 s. The default 12 s gives responsive SAM engagement while keeping API overhead low on large Syria networks.

AIR_INTERCEPT_INTERVAL25 sHow often intercept zones are checked for enemy aircraft.▼ details

Every 25 seconds the script checks whether any enemy aircraft are inside any coalition trigger zones. If so, and if the assigned squadron has available (alive, not currently airborne) flights, one flight is scrambled.

25 s means up to a 25-second delay between an aircraft entering a zone and a scramble order. At 900 km/h an aircraft travels ~6.25 km in 25 s — increase the zone radius if you want tighter response, or lower to 10 s for more reactive scrambles at the cost of higher API load.

WEAPON_TRACK_INTERVAL5 sHow often in-flight weapons are scanned for ARM threats.▼ details

Every 5 seconds the script iterates every weapon in trackedWeapons[]. It checks: is this weapon still alive? Is it an ARM type? Is it heading towards any of our radar groups? If yes, that radar shuts down for ARM_SHUTDOWN_TIME seconds.

5 seconds is responsive enough for ARM tracking — ARMs typically fly for 20–60 seconds so sub-second tracking has no benefit. The 5 s interval keeps the tracking cost low during large engagements with many in-flight weapons while maintaining fully reactive ARM defence.

RTB_CHECK_INTERVAL15 sHow often airborne intercept flights are checked for bingo fuel.▼ details

Every 15 seconds all active (airborne) intercept flights are checked. For each flight, every unit's Unit:getFuel() is called, which returns a 0.0–1.0 fraction of internal fuel capacity. If any unit is at or below GCI_FUEL_RTB_THRESHOLD the flight is ordered to RTB.

15 s is a reasonable polling rate. Fuel burn is slow enough that a 15-second gap between checks won't cause a flight to flame out before receiving the RTB order. Lower to 5 s for very short-range aircraft.

NODE_REFRESH_INTERVAL900 s (15 min)How often the SAM and EWR node lists are fully rebuilt from scratch.▼ details

On startup buildNodeList() scans all coalition ground groups and builds the SAM and EWR node lists from naming prefixes. Every 15 minutes it runs again to pick up any dynamically spawned groups.

Dead-node handling: Between full rebuilds, the main IADS loop (every UPDATE_INTERVAL) calls pruneDeadNodes() which iterates the existing node lists and removes any group whose :getSize() returns 0 or whose :isExist() returns false. This is a lightweight check with no coalition.getGroups() API calls, keeping the lists current without waiting for the 15-minute rebuild.

Reduce to 300 s for fast-paced missions with rapid SAM losses. Increase to 1800 s on low-spec servers.

Configuration — Detection

Detection is handled automatically. The script uses coalition.getDetectedTargets() as its primary sensor source (DCS native radar model) with a coalition.getGroups() scan as fallback when the primary API is unavailable. There are no per-coalition detection range knobs — coverage is governed entirely by the DCS radar model and SAM engagement range. See the Detection Pipeline deep-dive for full details.

CONTACT_IGNORE_PREFIXESBLUE_AWACS_, RED_AWACS_Unit name prefixes excluded from contact lists regardless of detection method.▼ details

An array of unit name prefix strings. During gatherContacts(), any unit whose name starts with one of these prefixes is silently discarded even if it was returned by the DCS radar sensor model. The default entries prevent BLUE and RED AWACS flights from appearing as SAM targets.

DCS surfaces some units tagged as invisible in the ME (AWACS, FAC, tankers) via coalition.getDetectedTargets(). Adding their group prefix here keeps them out of the contact lists without needing to change any ME settings.

CONTACT_IGNORE_PREFIXES = {
    "BLUE_AWACS_",
    "RED_AWACS_",
    "BLUE_TANKER_",  -- example: exclude tankers
}
IMMORTAL_IADS_NETWORKS{ LEBANON = true }Networks whose radars are never suppressed in response to incoming weapons.▼ details

A hash map of sub-IADS network names to true. When suppressSAMRadar() is called for a SAM in a network listed here, the suppression is skipped entirely — the radar stays on and the SAM never evacuates. Use this for networks whose units are set Immortal in the Mission Editor; since they cannot actually be killed by an ARM, there is no benefit to shutting down or relocating.

The Lebanon sub-IADS is immortal by design, providing persistent layered defence regardless of SEAD pressure. Remove the entry if you want Lebanon SAMs to react to ARM threats like a normal network.

Configuration — SAM Range Table

Per-type missile envelope table. getSAMRange() walks the first launcher unit in a group, matches its :getTypeName() against keys in this table (plain string.find, case-sensitive), and returns {min, max} metres, or nil if no pattern matches. Results are lazy-cached in _samRangeCache for the session.

Groups whose launcher type matches no pattern skip the Lua-side range gate entirely — the EngageUnit task is still issued and DCS decides at controller level whether the SAM can reach the contact.

Configuration — SAM Engagement

SAM_MIN_ENGAGE_ALT20 m AGLMinimum altitude for a contact to be considered a valid SAM target.▼ details

Contacts below this altitude (metres, from pos.y) are filtered out of the engagement queue. This prevents the IADS from fixating on ground vehicles, boats, or aircraft that are taxiing. 20 m is essentially at ground level — any airborne threat qualifies.

Raise to 100 m if you want the IADS to ignore nap-of-earth helicopter ingress. Set to 0 to let SAMs engage anything including vehicles (rarely useful).

SAM_FIRE_DELAY_MIN / MAX0 – 1 sRandom reaction delay before a SAM fires once it has a valid firing solution.▼ details

Once a SAM wins the engagement scoring contest, a random delay between SAM_FIRE_DELAY_MIN and SAM_FIRE_DELAY_MAX is applied before the actual fire order. This prevents all SAMs firing simultaneously in the same DCS frame, which looks unnatural and can cause missile spawn issues.

The 0–1 s window makes the IADS react near-instantly — the minimum is 0 (immediate response) with a minimal random jitter up to 1 s for natural variation. Raise the max to 5–10 s for a noticeably sluggish network.

PKill_BASE0.92Base probability-of-kill used in the SAM scoring formula.▼ details

The engagement scoring formula is: score = PKill_BASE × altFactor × rangeFactor × healthFactor. The SAM with the highest score engages. PKill_BASE is the baseline for a healthy SAM unit with the target perfectly on boresight at optimal range.

Factors reduce the score: targets at very low altitude drop altFactor, targets near the edge of range drop rangeFactor, damaged SAMs drop healthFactor. The score is relative — it determines which SAM gets the shot, not whether the missile actually hits (that's DCS's own miss calculation).

Changing PKill_BASE doesn't make SAMs more or less lethal in isolation; it shifts the scoring baseline and affects which SAM gets selected when multiple equally-positioned SAMs compete for the same target.

SAM_MIN_ENGAGE_SCORE0.18Minimum Pk score a SAM needs before it will fire. Prevents wasted shots.▼ details

After the scoring formula computes a value for every SAM–contact pair, the result is compared to this threshold. If the score is below it, the SAM holds fire regardless of whether it is the best available shooter. This prevents damaged SAMs at extreme range from wasting missiles on hopeless shots.

At the current 0.18, the threshold is aggressive — the IADS will take long-range and edge shots. Only truly unworkable geometry is skipped: severely damaged batteries at extreme range against low-altitude contacts.

Configuration — ARM Defence

ARM_SHUTDOWN_TIME90 sHow long a radar stays silent (EMCON) after detecting an incoming ARM.▼ details

When the weapon tracking loop identifies an ARM heading for a radar group, that radar stops emissions and the suppression end time is recorded. For the next 90 seconds the group is excluded from SAM engagement scoring — radars stay dark even if non-ARM contacts are in view during that window.

90 seconds covers the full terminal flight time of an AGM-88 HARM launched from its maximum practical standoff range (~180 km at altitude). The SAM stays dark for the entire follow-on strike window and cannot simply be waited out by launching a quick second pass after the ARM has flown clear.

Reduce to 60 s for a more forgiving EMCON window. Reduce to 28 s for a short window where tight SEAD timing is rewarded — the radar comes back online while the HARM is still in flight at long range.

ARM_MOVE_RADIUS800 mDistance a mobile SAM randomly relocates when an ARM is detected.▼ details

If the targeted SAM group contains mobile units (e.g. Pantsir, Buk, S-300 TELs) this value defines the radius of the random relocation offset applied when an ARM is detected. The group moves to a random point within this radius of its current position.

800 m is enough to cause a HARM with a ~50 m CEP to miss. Increase to 1500–2000 m for a more dramatic scoot response, but note that large moves on hilly terrain may place a unit in an obstacle — DCS doesn't pathfind random moves.

For static sites (e.g. fixed S-300 launchers) this value is irrelevant because the movement command is ignored by non-mobile units.

Configuration — Threat Prioritisation

Each contact’s engagement score is multiplied by a threat-class weight so the IADS allocates its best SAMs to the most dangerous threats regardless of geometry. Threat class is confirmed by weapon fire, not airframe-name assumptions — so multi-role aircraft start as Fighter and upgrade only when they actually fire.

Weapon-fire confirmation: S_EVENT_SHOT maintains _confirmedSEAD{} (fired an ARM) and _confirmedStrike{} (fired an AGM). Only dedicated SEAD-only airframes (EA-18G, EA-6B, EF-111, MiG-25BM) default to SEAD class without a confirmed shot. An F-16C starts as Fighter and upgrades to SEAD if/when it fires a HARM.
THREAT_PRIORITY.SEAD_WEIGHT3.0Score multiplier for confirmed SEAD aircraft (ARM shooters).▼ details

The highest priority weight. SEAD aircraft actively hunting radar sites are the most dangerous threat to the IADS network. A 3.0 multiplier ensures the best available SAM is always assigned to the SEAD contact even if a strike aircraft has better raw engagement geometry.

THREAT_PRIORITY.STRIKE_WEIGHT2.0Score multiplier for confirmed strike aircraft (AGM shooters, not already SEAD).▼ details

Aircraft confirmed to be in a ground-attack role. Prioritised above fighters and helicopters because they represent a direct threat to ground assets.

THREAT_PRIORITY.FIGHTER_WEIGHT1.2Default multiplier for unconfirmed-role or air-superiority aircraft.▼ details

Applies to any aircraft not yet confirmed as SEAD or Strike, including dedicated air-superiority fighters and multi-role aircraft before they fire a ground weapon. Slightly prioritised above helicopters.

THREAT_PRIORITY.HELO_WEIGHT0.8Score multiplier for rotary-wing contacts.▼ details

Helicopters are de-prioritised relative to fast jets. Long-range SAMs prefer fast-jet threats; SHORAD units (which specifically engage low-altitude contacts) handle helicopter suppression.

Configuration — Geographic Sectors

SAM nodes are automatically assigned to geographic sectors based on physical proximity to ME trigger zones. Contacts detected outside a SAM’s assigned sector incur a score penalty, steering the network toward local SAM–to–local threat allocation rather than long cross-map assignments.

SAM_OUT_OF_SECTOR_PENALTY0.25Score multiplier for SAMs engaging contacts outside their assigned sector zone.▼ details

When optimizeEngagements() scores a SAM against a contact, it checks whether the contact’s position is inside the SAM’s assigned zone (determined at startup by buildSAMSectorCache()). If not, the score is multiplied by 0.25. An out-of-sector SAM needs to score 4× higher than the best in-sector candidate to win the assignment — preventing cross-sector allocation except when the local sector is completely saturated.

Set to 1.0 to disable sector preference entirely. Set to 0.0 to hard-block out-of-sector engagements (use with care — a contact without any in-sector SAMs would be ignored).

Sector assignment is fully automatic from the ME trigger zone layout — no manual configuration needed. Each SAM is homed to whichever RED_ZONE_* / BLUE_ZONE_* / LEBANON_ZONE_* centre is closest to its current position. Assignment refreshes every NODE_REFRESH_INTERVAL.
SHORAD_HANDOFF_ENABLEDtrueEnables the independent SHORAD engagement pass in optimizeEngagements().▼ details

When true, a dedicated SHORAD pass runs after the primary SAM assignment loop each tick. SHORAD units engage any contact in their envelope independently — they do not wait for a long-range SAM to be assigned first. A Pantsir fires on an aircraft within its range even if no SA-10 or SA-17 is engaged at all.

SHORAD units are identified by two checks (either is sufficient): the group name contains SHORAD_NAME_PATTERN (default "SHORAD"), OR the group’s max engagement range in SAM_RANGE_TABLE is ≤ SHORAD_MAX_RANGE (default 25,000 m). This protects groups like Pantsir and Tor batteries not literally named *SHORAD*.

Set to false to disable independent SHORAD engagement. SHORAD units will still compete in the normal primary scoring loop but will not get a dedicated second pass.

SHORAD_NAME_PATTERN“SHORAD”String that identifies a SAM group as SHORAD by name.▼ details

Any SAM group whose name contains this exact substring (case-sensitive) is treated as SHORAD throughout the script: kept radar-on permanently, never suppressed by ARM events, and participates in the independent SHORAD engagement pass. The default "SHORAD" matches names like RED_SAM_SHORAD_Pantsir_01.

Change to any other string to match your mission’s naming convention.

SHORAD_MAX_RANGE25,000 mMax missile range threshold that also classifies a group as SHORAD.▼ details

If a SAM group’s maximum range in SAM_RANGE_TABLE is ≤ this value, it is treated as SHORAD regardless of its name. This ensures Pantsir-S1 (max 20 km), Tor-M1 (max 12 km), and similar short-range systems not named with "SHORAD" receive all SHORAD protections: permanent radar-on, ARM-suppression immunity, and the independent engagement pass.

Groups not in SAM_RANGE_TABLE at all are not matched by this check — only the name pattern applies. Set to 0 to rely purely on name-based detection.

Configuration — Air Intercept

INTERCEPT_ALTITUDE6,000 mAltitude (metres) assigned to scrambled intercept flights.▼ details

When a flight is scrambled, their intercept waypoint is set to this altitude. 6,000 m (approximately FL200) is a good medium-high intercept altitude for most threats — above most Man-PAD / AAA while below typical BARCAP altitudes.

Increase to 8,000–10,000 m for threats that fly at medium-high altitude (cruise missiles, strike packages). Decrease to 4,000 m for a low-altitude intercept role.

INTERCEPT_SPEED900 km/hSpeed (km/h) set for intercept waypoints.▼ details

The indicated airspeed set on the intercept waypoint. 900 km/h is a reasonable intercept speed for most fighter aircraft — fast enough to close quickly without burning excessive fuel. Increase to 1,100+ km/h for more aggressive intercepts. DCS AI may ignore this value if it exceeds the aircraft's max speed.

RTB_LOITER_TIME0 sHow long a flight loiters after the threat zone clears before RTB is ordered.▼ details

After an intercept zone goes empty (no more enemy contacts), the script waits this many seconds before ordering RTB. At 0 (the current default) RTB is issued immediately the moment the zone clears — flights do not linger.

Increase to 30–120 s if you want fighters to patrol briefly after clearing a zone, reducing the chance of a rapid re-entry catching them on the ground rearming. Note that the leash check (INTERCEPT_LEASH_BUFFER) can still recall flights that stray too far, regardless of this timer.

SCRAMBLE_THREAT_BUFFER0 mExtra radius beyond the zone boundary that still counts as a threat for scramble purposes.▼ details

Added to the zone’s zd.radius when getThreatsForZone() checks for threats. At 0 (current default), the enemy aircraft must be physically inside the zone boundary (dist2d ≤ zd.radius) before a scramble is ordered.

Increase to 40,000–80,000 m to scramble intercept flights when an enemy is still approaching the zone, giving fighters time to climb and position before the intruder crosses the boundary. At the default of 0, zones must be sized generously enough to provide that lead time themselves.

INTERCEPT_LEASH_BUFFER80,000 mMaximum distance beyond zone radius before an airborne flight is force-recalled.▼ details

The flightMaintenanceLoop() compares each airborne flight’s distance from its assigned zone centre against zd.radius + INTERCEPT_LEASH_BUFFER. If the flight has strayed further than this, it is immediately recalled via orderFlightRTB() regardless of threat status or RTB_LOITER_TIME.

80 km (80,000 m) gives fighters enough room to prosecute a threat that has been engaged beyond the zone boundary without immediately recalling them, while preventing fighters from chasing targets deep into friendly territory or being permanently lost to AI pathfinding.

Reduce to 40,000 m for tightly contained engagement areas. Increase to 120,000+ m if squadrons regularly need to pursue retreating threats well beyond the zone.

ZONE_PREFIX"RED_ZONE_"Naming convention prefix for airspace sector trigger zones.▼ details

Each squadron in SQUADRONS.RED has a zone field that must match a DCS trigger zone name exactly. The prefix is a convention you must follow when naming zones in the ME — it is not auto-prepended. Example: zone field "RED_ZONE_DAMASCUS" must exactly match a trigger zone of that name in the mission file.

Use circles, not polygons. The script reads zd.radius and zd.point from MIST's zone database and performs a simple 2D distance check — it does not use DCS's native polygon inside/outside test. For a polygon zone MIST provides the bounding-circle radius (centre to furthest vertex), so the actual polygon shape is ignored and the check is always circular. A long thin polygon will behave like a large circle enclosing it, triggering scrambles for contacts that are geometrically outside the polygon but inside its bounding circle. Stick to circle zones for correct behaviour.

Configuration — GCI / AWACS

AWACS aircraft (groups matching RED_AWACS_ or BLUE_AWACS_) are kept on orbit by a background keeper loop. There are no player-facing picture broadcasts — the script operates as a silent backend IADS with no HUD messages except an activation notice at mission start and dispatch errors.

GCI_FUEL_RTB_THRESHOLD0.20 (20%)Fuel fraction at which an intercept flight is ordered to RTB.▼ details

The threshold is compared against Unit:getFuel() which returns a 0.0–1.0 fraction of internal fuel. External tanks are NOT included — DCS's getFuel() only reports internal fuel regardless of loadout. A Hornet with drop tanks may actually have far more total fuel than the script can detect.

0.20 (bingo 20%) is reasonable for most aircraft to still complete a divert. Extend to 0.30 for short-range aircraft (MiG-21, Harrier). The threshold is checked per unit, not per group — if any unit in the flight hits bingo, the entire group is called RTB.

System Deep-Dive — Detection Pipeline

Contact gathering runs every UPDATE_INTERVAL seconds via gatherContacts(coaName, enemyCoa). The script attempts the most realistic detection path first and falls back automatically if the DCS API is unavailable. Results are deduplicated by unit name in a seen table.

Primary Path — DCS Radar Model

coalition.getDetectedTargets(myCoaID, Unit.SensorType.RADAR) returns the objects currently detected by the coalition's own sensors. This is the same contact list DCS uses internally for its AI. It naturally respects terrain masking, ECM, RCS, and altitude effects. This path runs whenever the API is available (DCS 2.7+), which is the vast majority of cases.

Each returned object is filtered for: alive, enemy coalition, altitude > SAM_MIN_ENGAGE_ALT, not already in the seen list. Valid contacts are stored with position, velocity, detection time, and byRadar = true.

If coalition.getDetectedTargets() succeeds the function returns immediately — the fallback path is not run.

Fallback Path — coalition.getGroups() Scan

Only runs if the primary API throws an error or is unavailable. Scans all live enemy AIRPLANE and HELICOPTER groups and filters for airborne units: requires ground-speed > 30 m/s to exclude parked aircraft, taxiing aircraft, and late-activate frozen groups. Contacts are stored with byRadar = false.

A one-time log warning is written to dcs.log when the fallback activates: [IADS] INFO: coalition.getDetectedTargets unavailable – using coalition.getGroups fallback. SAM engagement ranges in optimizeEngagements() still act as coverage limits in fallback mode.

System Deep-Dive — SAM Scoring & Engagement

After contacts are gathered, each contact is scored against every live SAM node. The engagement sequence:

  1. At the start of each tick, a samCache is built once: position, health factor, and per-type range (from getSAMRange() — {min, max} for known types, nil for unrecognised) for each live SAM node. This is a single flat pass — scoring never calls Group.getByName() or getUnits() again after the cache is built.
  2. For each contact, every SAM is scored: score = PKill_BASE × rangeFactor × altFactor × healthFactor × threatWeight. Contacts outside a SAM’s per-type [min, max] envelope immediately score 0 and are skipped.
  3. Up to SAM_MAX_ENGAGE_PER_CONTACT SAMs (default 3) can be assigned to the same contact. The primary fires immediately; each subsequent SAM fires 1.5 s after the previous to saturate point-defence.
  4. The assigned SAM receives a randomised delayed fire order after SAM_FIRE_DELAY_MIN–SAM_FIRE_DELAY_MAX seconds to simulate crew reaction time.
  5. SAMs with no assigned contact have their radar shut off (setOnOff(false)) to reduce SEAD exposure. Only when the assignment actually changes is a DCS controller call made — avoiding hundreds of redundant API calls per tick on large networks.
The script assigns fire orders but DCS’s AI SAM controller ultimately decides whether to launch. If the target leaves the SAM’s DCS engagement envelope before the delay expires, the fire order may be ignored. This is correct behaviour.

System Deep-Dive — Pk Threshold Gate

The SAM_MIN_ENGAGE_SCORE constant (default 0.25) acts as a quality gate on every engagement. A SAM will only fire when its computed score exceeds this value.

The Scoring Formula

Score = PKill_BASE (0.92) × rangeFactor × altFactor × healthFactor × threatWeight

Each factor runs from 0.0 to 1.0 and they multiply together, so one bad factor drags the whole score down.

rangeFactor

Based on each SAM’s own {min, max} missile envelope from SAM_RANGE_TABLE — not a global range. Peaks at 60% through the envelope. At the minimum range edge the factor is 0.40; at maximum range it is 0.60; at 60% it reaches 1.00.

relD        = (range - minR) / (maxR - minR)   -- 0.0 at min, 1.0 at max
rangeFactor = 1 - abs(relD - 0.6)             -- peaks at relD=0.6 (score=1.0)

Example: S-300PS (min=5 km, max=120 km) optimal point = 5 + 60% × 115 = 74 km. Pantsir-S1 (min=0.2 km, max=20 km) optimal = 12 km. Tor (min=1.5 km, max=12 km) optimal = 7.7 km.

System Deep-Dive — ARM Defence

The 5-second weapon tracking loop iterates all in-flight weapons from the trackedWeapons[] list (populated by S_EVENT_SHOT). For each weapon:

  1. Check its type name against ARM_TYPES using string.find() partial match — catches both underscore and hyphen DCS naming variants.
  2. If it is an ARM, extrapolate its velocity vector 60 s forward to estimate the aim point, then find the SAM node closest to that projected point.
  3. If the projected miss-distance is less than ARM_SUPPRESS_TRIGGER_DIST (default 150 km), trigger EMCON: record suppressedUntil[group] = timer.getTime() + ARM_SHUTDOWN_TIME. Also briefly suppress neighbouring SAMs within ARM_NEIGHBOR_SUPPRESS_RANGE (12 km).
  4. If the group has mobile units, apply a random positional offset up to ARM_MOVE_RADIUS.
  5. The suppressed group is skipped in the SAM scoring loop until the suppression expires; then radar is automatically restored.

Both ARM_TYPES and AGM_TYPES lists include dual-form DCS names (e.g. "AGM_88" and "AGM-88") to handle DCS version differences in weapon type-name formatting.

System Deep-Dive — Air Intercept Scramble

The 30-second intercept loop (gciInterceptLoop):

  1. For each zone, reads zd.point (zone centre) and zd.radius from trigger.misc.getZone(). To detect threats, the loop scans the cached enemy airplane group list directly (not IADS radar contacts) so scrambles trigger even if the enemy is in a notch or below radar coverage.
  2. 2D distance check: dist2d(unit.pos, zd.point) ≤ zd.radius. No additional buffer — the threat must be inside the zone boundary. This is always a circle test — polygon zone shapes are not respected.
  3. If any enemy is inside the zone and the squadron’s current airborne count is below maxFlights, find the next available (alive, not yet activated) group with the squadron’s groupPrefix.
  4. Activate the group via trigger.action.activateGroup() and assign a 4-second-delayed task: ROE weapons free, then either EngageUnit (if a live threat exists) or Orbit over zone centre at INTERCEPT_ALTITUDE and INTERCEPT_SPEED.
  5. The flight is registered in gciSt.flights for monitoring by the maintenance and fuel loops.

Pool exhaustion: when all numbered groups for a prefix are used (dead or activated), no more scrambles occur. Add more late-activate ME groups to increase the total sortie count.

System Deep-Dive — AWACS Orbit Keeper

A dedicated 300-second loop (awacsOrbitLoop) ensures all BLUE AWACS aircraft remain on orbit at the configured altitude and speed. On each tick:

  1. Scan all groups matching AWACS_PREFIX_BLUE (BLUE_AWACS_*).
  2. For each alive, active AWACS group, check whether its controller has a valid Orbit task.
  3. If the task is missing or stale, push a fresh Orbit task at AWACS_ORBIT_ALT_FT (default 30,000 ft) and AWACS_ORBIT_KTS (default 350 kts) over the group's current position.

This prevents AWACS aircraft from departing their orbit pattern after completing an ME waypoint list, and recovers from task loss caused by DCS AI interruptions. The loop only targets BLUE AWACS groups — RED AWACS are assumed to be scripted via ME waypoints or a separate management script.

The loop runs every 300 s (5 min). It will not override a valid in-progress orbit task. If an AWACS is shot down the keep loop silently skips it via groupAlive().

System Deep-Dive — RTB & Fuel Check

Every RTB_CHECK_INTERVAL seconds, for each active (airborne) flight:

  1. Iterate every unit in the group. Call unit:getFuel() which returns 0.0–1.0 (internal fuel only).
  2. If any unit's fuel ≤ GCI_FUEL_RTB_THRESHOLD, issue RTB waypoints back to homeBase. The RTB order is silent — no player message is broadcast, only a dcs.log entry.
  3. If the zone has been clear (no contacts) for ≥ RTB_LOITER_TIME, also issue RTB even if fuel is sufficient.
  4. Despawn/removal from active list occurs when DCS reports all units dead or when the group lands at the home base (altitude <10 m, speed <10 km/h near base).

System Deep-Dive — Node List Refresh

On startup and every NODE_REFRESH_INTERVAL seconds, buildNodeList() runs:

  1. Clears state.samNodes and state.ewrNodes.
  2. Calls coalition.getGroups(coaID, Group.Category.GROUND) — returns all live ground groups.
  3. Filters by prefix string matching, then checks groupAlive(name) (at least one unit with health >1%).
  4. Logs the counts: [IADS] RED IADS: 12 SAM nodes, 4 EWR nodes

System Deep-Dive — Threat Prioritisation

The scoring formula multiplies each SAM–contact pair’s raw Pk by the contact’s threatPriority weight before comparing across all contacts competing for the same SAM. A SEAD aircraft at medium range will outbid a fighter at perfect geometry, ensuring the network allocates its best shooters to the most dangerous threats first.

Threat Class Assignment (in gatherContacts())

  1. SEAD (weight 3.0) — unit name in _confirmedSEAD{} (fired an ARM this session), OR type matches SEAD_TYPE_PATTERNS (EA-18G, EA-6B, EF-111, MiG-25BM — dedicated SEAD-only airframes only).
  2. Strike (weight 2.0) — unit name in _confirmedStrike{} (fired a non-ARM AGM and not already SEAD).
  3. Helicopter (weight 0.8) — rotary-wing category.
  4. Fighter (weight 1.2) — default for all other aircraft.

Classification is persistent and one-way. An F-16C starts as Fighter; firing an AGM-65 during a strike promotes it to Strike; firing a HARM subsequently promotes it to SEAD for the rest of the session.

Why weapon-fire confirmation rather than airframe type? DCS returns "F-16C" for an F-16C regardless of what ordnance it is carrying. Checking the airframe name alone would classify every F-16C in a BARCAP role as a Fighter and every F-16C that loaded HARMs and then went cold as a permanent SEAD threat. Using S_EVENT_SHOT as ground truth means the IADS responds only to what pilots have actually done during the mission.

System Deep-Dive — Geographic Sector Auto-Assignment

On startup and every node-list refresh, buildSAMSectorCache(coaName, zonePrefix) automatically homes each SAM node to the nearest ME trigger zone. Contacts detected outside a SAM’s zone incur a SAM_OUT_OF_SECTOR_PENALTY score multiplier (default 0.25), favouring local SAM–to–local threat pairings across the map.

Assignment is fully automatic — no configuration required beyond placing ME trigger zones. The function iterates mist.DBs.zonesByName filtered to the coalition’s prefix (RED_ZONE_*, BLUE_ZONE_*, LEBANON_ZONE_*) and stores IADS[coaName].samSector[samName] = nearestZoneName. SAMs that move dynamically (ARM evasion relocation) are re-homed at the next nodeRefreshLoop() rebuild.

System Deep-Dive — SHORAD Independent Engagement

SHORAD units operate as an autonomous inner layer that runs independently of the long-range SAM assignment loop. They do not wait for an outer SAM to be engaged first — if a contact enters their missile envelope, they fire.

How SHORAD units are identified

Two checks are applied — either is sufficient for classification:

  1. The group name contains SHORAD_NAME_PATTERN (default "SHORAD", case-sensitive).
  2. The group’s max range in SAM_RANGE_TABLE is ≤ SHORAD_MAX_RANGE (default 25,000 m).

The range-based check ensures Pantsir-S1 (max 20 km), Tor-M1 (max 12 km), and any other short-range battery is correctly classified even without "SHORAD" in the group name (e.g. RED_SAM_THALAH).

SHORAD protections

  1. Permanent radar-on / weapons-free — the radar management pass never turns SHORAD off between assignments. The DCS AI keeps its sensor active continuously to react to missiles in milliseconds.
  2. ARM suppression immunity — suppressSAMRadar() returns immediately for any SHORAD-classified group. A HARM aimed at a nearby long-range SAM will not silence the Pantsir that should be shooting it down. This applies to both the primary target and the neighbour-suppression pass.
  3. Independent engagement pass — after the primary SAM scoring loop in optimizeEngagements(), a second pass iterates all SHORAD nodes and assigns them to any contact scoring above SAM_MIN_ENGAGE_SCORE in their envelope, regardless of whether a long-range SAM is already engaged against that contact.
SHORAD_HANDOFF_ENABLED must be true (the default) to activate the independent engagement pass. Radar management protection and ARM suppression immunity apply regardless of this flag.

System Deep-Dive — Dynamic SAM Reallocation

When a SAM unit is destroyed (S_EVENT_DEAD), the event handler immediately removes it from the coalition’s samNodes list and schedules optimizeEngagements() for 1 second later. This closes any coverage gap the destroyed battery was filling before the next normal iadsUpdateLoop() tick (up to 12 s later).

The reallocation is a full optimizeEngagements() run — all remaining live SAMs are re-scored against all current contacts and the best available assignments are issued. SAMs that retain the same assignment from the previous tick do not receive a redundant controller call (tracked via state.lastEngagement).

Players executing a DEAD strike can exploit the destroyed SAM’s gap for up to ~13 seconds (1 s reallocation delay + up to 12 s until next IADS tick). This is intentional — it rewards timely follow-on attacks while the network recovers.

Calculates a probability-of-kill score for a SAM engaging a specific contact. Accepts a pre-built cache entry rather than a SAM group name — no DCS API calls are made inside this function. The score drives which SAM wins the engagement assignment in optimizeEngagements().

optimizeEngagements(coaName)internal▼ details

The IADS engagement brain. Called each UPDATE_INTERVAL tick. Full sequence:

  1. Build samCache — a single flat pass over all live SAM nodes, storing {pos, health, rng} for each. This reduces per-tick DCS API calls from O(contacts × SAMs × SAM_MAX_ENGAGE_PER_CONTACT) to O(SAMs).

  3. Fire orders — primary SAM fires after a randomised SAM_FIRE_DELAY_MIN–SAM_FIRE_DELAY_MAX delay. Secondary and tertiary SAMs fire 1.5 s apart to saturate point-defence. A new controller call is only issued if the assigned target actually changed from the previous tick (tracked via state.lastEngagement), preventing redundant task resets every 12 s.
  4. Radar standby — SAMs with no assigned contact have their radar shut off (setOnOff(false)) to reduce SEAD exposure.

Lebanon sub-IADS additionally gates contacts to inside LEBANON_ZONES.

ParamTypeNotes
coaNamestring"RED" or "BLUE"

Returns: nothing — fires timer callbacks for each engagement order

Function Reference — ARM / AGM Defence

Three functions handle inbound anti-radiation missiles and other guided munitions.

suppressSAMRadar(coaName, samName)internal▼ details

Executes the full EMCON + move response for a SAM that has been identified as the likely ARM target:

  1. Turns radar off via setOnOff(false).
  2. Records suppressedUntil[samName] = now + ARM_SHUTDOWN_TIME — blocks optimizeEngagements() from assigning targets during the suppression window.
  3. Generates a random evasion offset via randomOffset(ARM_MOVE_RADIUS) and pushes a move Mission task. Mobile SAMs (Pantsir, SA-8, etc.) physically reposition; static sites attempt and fail gracefully.
  4. Schedules a timer at now + ARM_SHUTDOWN_TIME + 2 s. When it fires, if the suppression has expired and the group is still alive, radar is turned back on automatically.

coaNamestringDefending coalition.
samNamestringSAM group to suppress.

findARMTarget(wpnPos, wpnVel, coaName) → samName, distinternal▼ details

Predicts which SAM node an in-flight ARM is targeting by extrapolating the weapon 60 seconds forward along its current velocity vector, then finding the SAM node closest to the projected impact point. Returns the predicted target name and the miss distance in metres.

This is a linear trajectory extrapolation — it does not model ARM seeker guidance or terminal manoeuvring. For typical terminal ARM profiles (HARM, ALARM, Kh-31P) a 60-second lookahead is sufficient to identify the target radar within 80 km with acceptable accuracy.

ParamTypeNotes

wpnVelVec3Current velocity vector (m/s).

Suppression is triggered in weaponTrackingLoop() when the projected miss distance is < ARM_SUPPRESS_TRIGGER_DIST (default 150,000 m). This prevents an ARM launched far away from suppressing SAMs in completely unrelated sectors.
alertSHORADtoEngageWeapon(weapon, coaName, skipSuppressed)internal▼ details

Called every tracking tick for in-flight ARM and AGM weapons. For each SAM node within range of the weapon, sets ROE and alarm state to engage. Two distance tiers:

  • CLOSE (≤ 50,000 m) — radar on, ROE weapons free (option 0 → 2), alarm red (option 9 → 2). The SAM is fully in the kill chain.
  • WARN (≤ 90,000 m) — radar on, alarm red only (tracking mode). SAM holds fire but activates its sensor to acquire the threat.

When skipSuppressed = true (ARM tracks), SAM nodes currently under suppressedUntil are skipped so the targeted SAM stays dark while nearby guns and IR SAMs can still attempt an intercept. When skipSuppressed = false (AGM tracks), all nearby SAMs are alerted regardless of suppression state.

coaNamestringDefending coalition.

Function Reference — Event Handler

eventHandler:onEvent(event)world event handler▼ details

The DCS world event handler registered once at startup via world.addEventHandler(eventHandler). Processes two event types:

S_EVENT_SHOT — fires when any unit launches a weapon. The handler:

  1. Gets the weapon type name via wpn:getTypeName().
  2. Checks it against IADS_CFG.ARM_TYPES and IADS_CFG.AGM_TYPES using string.find() partial match — so "HARM" in ARM_TYPES will match "AGM_88C_HARM".
  3. If it matches, determines the defending coalition from the initiator's coalition side.
  4. Appends an entry to trackedWeapons[] with the weapon object, ARM/AGM type flags, defending coalition name, and the detection timestamp.

S_EVENT_DEAD / S_EVENT_CRASH — fires when a unit is killed or crashes. Checks if the unit belongs to a tracked intercept flight and marks that flight's status as "dead" in gciState[coalName].flights.

The event handler feeds trackedWeapons[] and flight status tables. It does not directly suppress radars or order RTBs — those actions happen in the timer loops that consume this data.

Function Reference — Timer Loops

Seven self-rescheduling timer callbacks drive all runtime behaviour. Each returns its own next execution time via the DCS timer.scheduleFunction() API.

weaponTrackingLoop() → nextTimetimer — 5 s▼ details

Runs every WEAPON_TRACK_INTERVAL (5 s). Iterates trackedWeapons[]. For each tracked weapon:

  • Calls wpn:getPoint() inside pcall(). If the call fails or returns nil, the weapon has impacted or expired and is dropped from the list. A 300-second TTL also prunes weapons that somehow never return nil (mod weapons, DCS edge cases).
  • ARM weapons not yet alerted: calls findARMTarget(); if miss distance < ARM_SUPPRESS_TRIGGER_DIST (default 150,000 m), calls suppressSAMRadar() on the predicted target and sets wt.alerted = true to prevent repeated suppression.
  • ARM weapons already alerted: calls alertSHORADtoEngageWeapon(skipSuppressed=true) every tick so nearby SHORAD can attempt an intercept while the targeted SAM stays dark.
  • AGM weapons: calls alertSHORADtoEngageWeapon(skipSuppressed=false) every tick — continuously re-alerts all nearby SHORAD as the weapon approaches.

At the end of each tick, trackedWeapons is replaced with the filtered active-only array.

Returns: timer.getTime() + WEAPON_TRACK_INTERVAL

iadsUpdateLoop() → nextTimetimer — 12 s▼ details

The main IADS heartbeat. Runs every UPDATE_INTERVAL (12 s). Each tick performs the full detection-to-engagement pipeline for all three coalition sub-IADS (RED, BLUE, LEBANON) in sequence:

  1. pruneDeadNodes() × 3 — lightweight incremental removal of destroyed SAM/EWR groups without full API calls.
  2. gatherContacts() × 3 — rebuilds all three contact lists; uses DCS native radar model (primary) or coalition group scan (fallback) per-unit.
  3. optimizeEngagements() × 3 — scores and assigns SAM engagements for all contacts in RED, BLUE, and LEBANON.

Returns: timer.getTime() + UPDATE_INTERVAL

gciInterceptLoop() → nextTimetimer — 25 s▼ details

Runs every AIR_INTERCEPT_INTERVAL (25 s). For each coalition, for each configured squadron:

  1. Calls getThreatsForZone() for the squadron's assigned zone using a pre-cached enemy airplane group list (cached once per coalition per tick to avoid redundant API calls).
  2. Threats present: resets clearSince; computes need = min(threats, maxFlights) − countAirborne(); calls dispatchFlight() for each needed scramble.
  3. No threats, flights airborne: starts or advances clearSince. Once clearSince ≥ RTB_LOITER_TIME, calls orderFlightRTB() for every airborne flight in the squadron.

Returns: now + AIR_INTERCEPT_INTERVAL

flightMaintenanceLoop() → nextTimetimer — 15 s▼ details

Runs every RTB_CHECK_INTERVAL (15 s). Iterates all flights marked "airborne" in both coalition flight registries. For each:

  • Verifies the DCS group still exists. If not → marks status "dead".
  • Iterates alive units tracking the lowest fuel fraction via unit:getFuel() (0.0–1.0, internal tanks only).
  • If no alive units → marks status "dead".
  • If lowestFuel ≤ GCI_FUEL_RTB_THRESHOLD → calls orderFlightRTB() with a bingo message including the actual percentage.

Returns: timer.getTime() + RTB_CHECK_INTERVAL

nodeRefreshLoop(_, time) → nextTimetimer — 900 s▼ details

Runs every NODE_REFRESH_INTERVAL (900 s / 15 min). Calls buildNodeList() for all three coalition sub-IADS (RED, BLUE, LEBANON) — the definitive cleanup pass that permanently removes any SAM or EWR group destroyed since the previous full refresh. While iadsUpdateLoop() calls pruneDeadNodes() every 12 s for lightweight incremental dead-group removal without API calls, nodeRefreshLoop() serves as the authoritative long-period full rebuild ensuring no stale entries persist.

Returns: time + NODE_REFRESH_INTERVAL

awacsOrbitLoop(_, time) → nextTimetimer — 300 s▼ details

Runs every 300 s (5 min). Checks all alive BLUE AWACS groups. For each group, compares the current altitude of the lead unit against AWACS_ORBIT_ALT_FT (default 30,000 ft). If the altitude has dropped more than 1,000 ft below the target, pushes a fresh Circle Orbit task at the configured altitude and speed (AWACS_ORBIT_KTS). Groups that are already flying at the correct altitude are left undisturbed. Silently skips groups that have been destroyed via groupAlive().

This prevents AWACS aircraft departing their orbit after completing an ME waypoint list, and recovers from orbit task loss caused by DCS AI interruptions. RED AWACS are not managed — they are assumed to be scripted via ME waypoints.

Returns: time + 300

memoryCleanupLoop() → nextTimetimer — 600 s▼ details

Runs every MEM_CLEANUP_INTERVAL (600 s / 10 min). A full housekeeping pass that purges accumulated table entries which per-tick operations may miss:

  1. Flight record purge — removes gciState.flights entries with status "dead" or "standby". Keeps countAirborne() and getAvailableFlights() operating on a small active-only set rather than the full mission history.
  2. Suppression timer purge — clears expired suppressedUntil entries and entries for SAM groups that no longer exist. Catches entries missed by the per-tick pruneDeadNodes().
  3. Weapon entry hard-purge — belt-and-suspenders TTL pass: removes any tracked weapon entry older than 360 s, guarding against mod weapons or DCS edge-cases that never return nil from getPoint().
  4. Stale contact purge — removes IADS[coaName].contacts entries whose DCS unit no longer exists or has been killed between ticks.

Logs a one-line summary to dcs.log: [MemClean] cycle complete — purged: N flight records | N suppress timers | N weapon entries | N stale contacts.

Returns: now + MEM_CLEANUP_INTERVAL

Function Reference — Scramble & RTB

dispatchFlight(groupName, coalName, sqd, threats, gciSt)internal▼ details

Activates a late-activate intercept group, registers it as airborne, and assigns the intercept task. Fully silent — no player-facing output. Full sequence:

  1. Activate — trigger.action.activateGroup(g) spawns the group from late-activate state. If Group.getByName() returns nil, logs an error and aborts.
  2. Register — adds an entry to gciSt.flights[groupName] with status "airborne", zone, homeBase, callsign, coalition, and launch time.
  3. Delayed task (4 s) — a timer fires 4 seconds after activation. Sets ROE weapons free (option 0 → 2) and aggressive threat reaction (option 1 → 0). If a live threat unit is available → EngageUnit. If not → Orbit over zone centre at INTERCEPT_ALTITUDE and INTERCEPT_SPEED.

The 4-second delay is required because the group controller may not be ready immediately after activate() — tasking too quickly results in tasks being silently dropped by DCS.

groupNamestringLate-activate group name (e.g. "RED_AIR_DAMASCUS_01").
coalNamestring"RED" or "BLUE"
sqdsquadron tableProvides zone name, homeBase, callsign.
threatsarrayContacts from getThreatsForZone(). First entry is the primary target.
gciSttablegciState[coalName]

Returns: nothing

orderFlightRTB(groupName, gciSt, reason)internal▼ details

Orders an airborne intercept flight to return to base and eventually despawn. Full sequence:

  1. Resolves fState.homeBase via Airbase.getByName(); falls back to getNearestAirbase() if not found.
  2. Sets ROE to return-fire only (option 0 → 4).
  3. Pushes a two-waypoint Mission task: current position → Landing at home airbase.
  4. Marks flight status "rtb".
  5. Logs the RTB order to dcs.log with the reason string.
  6. Schedules a cleanup timer +600 s (10 min). When it fires, if status is still "rtb": calls group:destroy() and sets status to "standby", making the group name available for a future scramble cycle.

gciSttablegciState[coalName]

After the 600 s cleanup the group is destroyed in DCS, not returned to late-activate state. For reliable multi-sortie cycles, add additional late-activate intercept groups in the ME.

Function Reference — Initialisation

init()startup — runs at T+1 s▼ details

Master initialisation. Called via a 1-second delayed timer (at the bottom of the script) to ensure MIST is fully loaded before any IADS logic executes. Sequence:

  1. Validates MIST is loaded — logs the MIST version to dcs.log. (math.randomseed is not called — DCS sandboxes it; math.random() works correctly without explicit seeding.)
  2. Calls validateSquadrons() — checks every squadron groupPrefix against the MIST group database and logs counts to dcs.log (useful for catching ME naming mismatches at startup).
  3. Calls discoverZones() — registers all RED_ZONE_* and BLUE_ZONE_* trigger zones from MIST DB.
  4. Calls buildNodeList() for RED, BLUE, and LEBANON — populates initial SAM/EWR node arrays for all three coalition sub-IADS.
  5. Schedules the runtime timer loops with staggered offsets:
    • weaponTrackingLoop at T+5 s
    • iadsUpdateLoop at T+10 s
    • gciInterceptLoop at T+15 s
    • awacsOrbitLoop at T+20 s
    • flightMaintenanceLoop at T+30 s
    • memoryCleanupLoop at T+MEM_CLEANUP_INTERVAL
  6. Schedules nodeRefreshLoop at T+900 s (first full node rebuild at 15 min).
  7. Broadcasts "[IADS] RED/BLUE Integrated Air Defence + Red Air Intercept ACTIVE" via trigger.action.outText (10 s, visible to all players).

Returns: nothing
