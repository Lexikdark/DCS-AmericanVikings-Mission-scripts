DGSS Leaderboard System

DGSS-Leaderboard 3.5.lua  ·  Player kill, CSAR, logistics & convoy tracking with persistent scoring

How It Works

The Leaderboard system tracks player activity across multiple categories and assigns a weighted point score. It uses DCS event handlers for kills and deaths, periodic polling for logistics and resupply, and public API functions that other DGSS scripts can call directly (e.g. DGSS_LEADERBOARD.addCSARRescue()).

Configuration — Supply & Distribution Zones

SUPPLY_BASE"KANDAHAR"Main supply base trigger zone name.▼ details

The primary zone where supply units originate. When a tracked supply unit returns to this zone, its delivery tracking is reset. Also used as a resupply origin for aircraft fuel tracking.

SUPPLY_HELIPORT{"KANDAHAR","FOB_URGOON"}Additional supply pickup zones (heliports/FARPs).▼ details

Array of trigger zone names that also count as supply origins. Supply units leaving these zones are tracked for delivery credit.

DISTRIBUTION_BASES10 zonesDelivery destinations where logistics score is awarded.▼ details

Array of trigger zone names: KABUL, BAGRAM, JALALABAD, FOB_LONDON, FOB_DALLAS, FOB_PARIS, FOB_WARSAW, FOB_SALERNO, FOB_URGOON, TARINKOT. A crate or cargo unit arriving in one of these zones credits the nearest helicopter player.

Configuration — Supply Unit Types

The script recognises supply cargo via two methods:

  1. Exact type match — DCS unit type name appears as a key in DGSS_LEADERBOARD.SUPPLY_UNIT_TYPES (e.g. "ammo_cargo", "iso_container").
  2. Keyword match — case-insensitive string.find for: cargo, crate, container, ammo, barrel, sling, fuel, iso, supply.
If you add custom cargo types, either add them to SUPPLY_UNIT_TYPES or ensure the type name contains one of the keywords above.

Configuration — Timing

Logistics tracker12 sHow often supply movement, warehouse changes, and aircraft resupply are polled.▼ details

The logisticsTracker() function runs every 12 seconds. It calls trackSupplyMovement() (iterates BLUE ground groups for cargo units), trackWarehouseLogistics() (checks warehouse inventory changes at distribution bases), and trackAircraftResupply() (checks fuel levels of player aircraft at distribution bases).

Player scanner60 sHow often new players are detected and initialised.▼ details

scanForNewPlayers() iterates all BLUE airplane and helicopter groups every 60 seconds. New player names are initialised in PLAYER_STATS and a save is triggered immediately so joining players are persisted.

Menu poller60 sHow often F10 Leaderboard menus are created for new player groups.▼ details

leaderboardMenuPoller() checks all BLUE airplane and helicopter groups every 60 seconds. Existing menus are tracked in UNIT_MENUS and only created once per unit (v3.5 optimisation — interval increased from 10 s to 60 s).

Cleanup loop60 sHow often dead/stale tracking entries are purged.▼ details

cleanupTrackingTables() runs every 60 seconds. It removes entries for destroyed units from UNIT_TRACKING, AIRCRAFT_TRACKING, and UNIT_MENUS. It also purges stale timestamps (>10 min) from anti-duplicate tables and old landing/warehouse delivery records.

Auto-save900 s (15 min)How often player stats are written to disk.▼ details

autoSaveStats() calls DGSS_LEADERBOARD.saveStats() every 15 minutes. Stats are also saved immediately when a new player joins. The save file is a plain Lua table that can be manually edited.

Tracking — Kills & Deaths

Uses world.addEventHandler to catch:

  • S_EVENT_KILL — credits initiator:getPlayerName() with a kill.
  • S_EVENT_PILOT_DEAD / S_EVENT_DEAD — records a death for the player. Anti-duplicate guard: ignores duplicate events within 1 second of each other.

Tracking — CSAR Rescues

The CSAR system calls DGSS_LEADERBOARD.addCSARRescue(playerName) directly when a pilot is rescued. No polling required — the leaderboard exposes this as a public function.

Tracking — Logistics (Crate/Cargo Delivery)

Every 12 seconds trackSupplyMovement() iterates BLUE ground groups looking for supply-type units. When a cargo unit enters a distribution base zone:

  1. The nearest helicopter (<200 m) with a player name is identified as the delivery pilot.
  2. The unit is marked as delivered to prevent double-counting.
  3. Tracking resets when the unit returns to a supply base.

Additionally, trackWarehouseLogistics() monitors warehouse inventories at distribution bases. If a significant increase (>100 units of any category) is detected within 2 minutes of a player landing, the player is credited.

Tracking — Aircraft Resupply

trackAircraftResupply() monitors fuel levels of player aircraft at distribution bases. If a player's fuel increases above 70% while at a distribution base (not the supply base), they are credited with an aircraft resupply. Anti-duplicate: 5-second cooldown per unit.

Tracking — Convoy Operations

Other scripts call DGSS_LEADERBOARD.addConvoyCompletion(playerName, successState) where successState is "full", "partial", or "failed". Similarly, addConvoyRescue(playerName) is called when a player rescues a convoy crew.

File Persistence

FilePath
leaderboard_stats.luaSaved Games\DCS[.openbeta]\Mission Saves\leaderboard_stats.lua

The save file is a plain Lua table (LEADERBOARD_DATA) assigning each player name to their stats. On load, the file is loadstring-executed to restore PLAYER_STATS. A fresh save is written immediately on init to ensure the file exists.

The file can be manually edited to seed scores, remove players, or reset the leaderboard. Delete the file to start fresh.

Mission Editor Checklist

  1. Un-sanitize io and lfs in your server's MissionScripting.lua.
  2. MIST (optional) — load mist.lua first if using other DGSS scripts.
  3. Load script — MISSION START → DO SCRIPT FILE → DGSS-Leaderboard 3.5.lua.
  4. Trigger zones — ensure SUPPLY_BASE, all SUPPLY_HELIPORT entries, and all DISTRIBUTION_BASES entries exist as trigger zones in the ME.
  5. Cargo objects — if using slingload logistics, place cargo static objects with type names matching SUPPLY_UNIT_TYPES or containing a recognised keyword.
  6. Integration — DGSS-CSAR+Lives, DGSS-CTLD, and convoy scripts should be loaded before the leaderboard so their globals exist when events fire. The leaderboard exposes its API immediately on load.
